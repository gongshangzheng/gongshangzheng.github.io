## 4.a · 术语表 + 领域问题定义（可选补洞）

如果 `survey-spine` 已经清楚写出术语表和领域问题定义，不再单独派发本步骤。只有当 Phase 3 缺少前置概念、问题边界或输入/输出定义时，才派 subagent 补洞：

### 术语表

从 Phase 0-3 全部素材中提取领域核心术语，每个术语：
- 一句话定义
- 一个类比或具体例子
- 区分"领域通用术语"和"特定论文自创术语"

### 领域问题定义

精确定义该调研领域的核心问题：
- 输入/输出空间
- 约束条件
- 优化目标
- 为什么这个问题重要
- 之前方案的具体局限（附数据）

### 派发模板

```
任务：执行 Phase 4a（术语表 + 领域问题定义）。
研究领域：<topic>
Phase 0-1 素材：~/Org/roam/note/<topic>/phase0-1-*.org
Phase 3 素材：~/Org/roam/note/<topic>/phase3-*.org
读取模板：~/.agents/skills/academic-research/subagents/terminology-problem.md
输出文件：~/Org/roam/note/<topic>/terminology-problem.md
```

输出的术语表和问题定义将作为后续写作 subagent 的统一参考。

## 4.0 · 章节骨架规划

在动笔之前，先规划文章的骨架结构。不同领域的调研适合不同的组织方式。

### 为什么需要这一步

Phase 3 的 `survey-spine` 已经是统一结构底稿。Phase 4 不再重新堆叠材料，而是把 `survey-spine` 转化为一篇读者可读的 survey：先建立问题，再建立 taxonomy，再解释方法演进和证据，最后给出取舍与开放问题。

### 第一步：从 `survey-spine` 抽取主线

通读 `survey-spine`，只做一次结构选择，不再默认设计三套方案。必须列出：

- **核心主问题**：这篇 survey 最终要回答什么。
- **读者路径**：读者先理解哪些前置概念，再进入哪些任务和技术路线。
- **核心分歧点**：领域内最有争议/最受关注的 2-3 个技术路线分歧。
- **方法演进主线**：最能体现领域发展的方法演进链。
- **关键证据锚点**：最重要的 5-10 个原文指针、具体指标、figure/table 或系统设计。
- **读者最可能困惑的点**：需要在正文中额外解释的概念边界。

### 第二步：选择一种叙事结构

根据 `survey-spine` 的主问题，直接选择最适合的结构。常见选项：

**A. 范式驱动结构**（Paradigm-Driven）
适用：领域由几个明确的技术范式/路线交替推动
结构：每个范式一个章节，内部按时间线叙述方法的演进
```
引言 → 范式一（对比学习）→ 范式二（统一理解+生成）→ 范式三（高效桥接）→ ...
```
优点：逻辑清晰，每个章节有独立的核心问题
风险：跨范式的工作（如 BLIP 同时属于多个范式）需要选择一个主要归属

**B. 时间线驱动结构**（Timeline-Driven）
适用：领域发展有明确的阶段性，每个阶段有核心共识的转变
结构：按时间段分章，每章涵盖该阶段所有重要工作
```
引言 → 第一阶段（对比学习确立）→ 第二阶段（统一架构）→ 第三阶段（高效桥接+指令微调）→ 展望
```
优点：读者能看到领域发展的全貌和转折点
风险：同一个方法的不同方面会被拆到不同章节

**C. 问题驱动结构**（Problem-Driven）
适用：领域围绕几个核心问题展开，不同方法是同一问题的不同解法
结构：每个核心问题一个章节，内部对比不同解决方案
```
引言 → 问题一（如何对齐视觉和语言？）→ 问题二（如何统一理解和生成？）→ 问题三（如何高效利用冻结大模型？）→ 展望
```
优点：对比性强，读者能清晰看到不同方法的取舍
风险：需要每个问题都有足够的"不同解法"来支撑对比

**D. 方法对比结构**（Method-Centric）
适用：领域内核心方法数量有限（5-10 个），且相互之间有明确的演进关系
结构：按方法维度（架构/训练目标/数据策略）分章，每章内做系统对比
```
引言 → 连接器架构对比 → 训练目标对比 → 数据策略对比 → 时间线总览 → 展望
```
优点：技术对比最深入
风险：叙事性弱，读起来像技术手册而非指南

### 第三步：写出唯一大纲

只输出一个最终大纲，不做三选一。大纲必须包括：

```
采用结构：[范式驱动 / 时间线驱动 / 问题驱动 / 方法对比 / 系列文章]
选择理由：[为什么这种结构最能回答主问题]
主线摘要：[5-8 句话说明整篇文章如何由浅入深推进]
章节目录：
  Section 1 · [标题] — [本章回答的问题，2-3 句话]
  Section 2 · [标题] — [本章回答的问题]
  ...
  Section N · [标题] — [本章回答的问题]
素材映射：[survey-spine 的哪些证据进入哪个 section]
关键风险：[这个结构可能遗漏什么，如何补救]
```

如果 `survey-spine` 不足以支持唯一大纲，退回 Phase 3 补证据，不要用多套大纲掩盖素材不足。

### 章节骨架标准要求

无论选择哪种结构，最终骨架必须满足：

- 开头 20% 篇幅必须由浅入深说明领域问题：任务输入/输出、生成对象、约束、为什么难、常见误解、最小术语表；不能开篇就罗列论文。
- 必须有 `任务 Taxonomy`：回答“要解决/生成什么”，每类写输入、输出、评测重点、代表论文、不适用场景。
- 必须有 `技术路线 Taxonomy`：回答“用什么表示/模型/系统路线解决”，每类写核心表示、适配任务、优势、限制、工程可得性。
- 必须有 `方法矩阵`：按表示、驱动信号、训练数据、输出形式、实时性、可控性、评测指标比较代表方法。
- 必须有 `时间线`：至少 3 个阶段，每阶段解释共识如何变化，而不是按年份列论文。
- 必须有 `开放问题`：至少 5 个问题，每个说明为什么仍未解决、受哪些证据支持。
- 每个章节有明确的**核心问题**（不是"这一段介绍了 X"而是"这一章回答了 Y"）。
- 章与章之间有逻辑递进或互补关系。
- 每个章节至少有 1 个具体证据锚点：原文指针、定量结果、表格、figure、系统设计或数据集描述。
- 每篇 `must-read-paper` 和 `route-representative` 必须在正文中有简要论述段落，不能只出现在表格、脚注或参考文献中。简要论述至少包括：它解决的问题、采用的技术路线、相对前后工作的变化、关键证据、局限，以及对应论文精读 HTML 链接。
- 每篇 `must-read-paper` 的核心图片必须进入最终 survey，用于解释方法结构、任务定义、结果对比或路线差异；若无可用论文原图，必须使用项目页/仓库图或 mermaid/jsxgraph 替代，并在 caption 中说明。

## 4.2 · 写作风格规范（教学式调研报告）

调研报告不是论文笔记的堆砌，也不是把多篇论文摘要拼成博客；它必须是一份**面向读者的结构化 survey**。

### 读者假设

- 有基础机器学习/深度学习背景
- 对该细分领域**不了解或仅了解皮毛**
- 希望快速建立系统认知，而非查阅原始论文
- 需要先理解“这个领域到底在建模什么问题”，再理解各路线为什么出现

### 段落级逻辑模板

每个章节的叙述必须遵循 **Motivation → Intuition → Mechanism** 三层递进：

1. **Motivation**（为什么需要这个方法）
   - 上一代方法留下了什么问题？
   - 这个问题的本质是什么？
   - 如果不解决会怎样？

2. **Intuition**（核心思想是什么）
   - 用类比或直觉解释核心创新（如："Q-Former 就像一个信息漏斗，只让与语言相关的视觉信息通过"）
   - 与读者已有知识的连接点
   - 为什么这个思路是自然的？

3. **Mechanism**（技术细节如何实现）
   - 具体架构设计
   - 训练策略
   - 关键工程选择及其原因

**禁止的写法**：
- ❌ "X 提出了 Y 方法，使用了 Z 技术，取得了好的效果。"（平铺直叙）
- ❌ 连续罗列三篇论文的贡献，没有叙事逻辑（论文堆砌）
- ❌ 直接上公式不解释意图（公式轰炸）

**推荐的写法**：
- ✅ "CLIP 只能'编码'，BLIP 让一个模型同时擅长理解和生成。核心思路是..."
- ✅ "反直觉发现：LLaVA 的简单 MLP 连接器在很多任务上表现优异，说明连接器复杂度不是瓶颈——数据质量和 LLM 能力更关键。"
- ✅ "在复杂公式前先用文字描述其'意图'：这个损失函数的目的是让匹配的图文对更接近，不匹配的更远离。"

### 教师口吻

- 使用"我们可以看到..."、"这意味着..."、"一个自然的疑问是..."
- 主动指出易混淆点和常见误解
- 在引入新概念时，先给直觉再给定义
- 使用对比帮助理解（"与 CLIP 的浅层对齐不同，GLIP 在编码器之间引入了深度跨模态融合"）

### 信息密度控制

- 每个段落承载一个完整的"认知单元"
- 段落之间有逻辑连接词（不是跳跃式切换话题）
- 方法对比必须包含具体指标和数值
- 引用论文时说明其在该叙事中的角色（"BLIP-2 确立了..."而非"BLIP-2 (Li et al., 2023) 提出..."）
- 原文指针只允许出现在中间材料、Review 记录和作者注释中；最终 HTML 正文必须把指针转写为真正的解释、证据说明和引用说明，不能出现 raw 路径、`file_path:start_line-end_line`、ledger 路径或“见原文指针”式占位。

### 字数与内容量约束

| 部分 | 最低要求 |
|------|---------|
| HTML 正文总量 | ≥ 5000 字（约 10KB） |
| 每个子方向/范式章节 | ≥ 600 字 |
| Survey 对标章节 | 必须引用已完整深读的 core-survey ledger / reference packet；逐篇比较 taxonomy、数据集、指标、局限，不得只做简短介绍 |
| 方法对比章节 | ≥ 1 个 4×5 以上表格 + 300 字叙述 |
| 时间线章节 | ≥ 3 个时间段，每个 ≥ 150 字 |
| 开放问题章节 | ≥ 5 个问题，每个 ≥ 50 字解释 |
| 重要论文论述 | 每篇 `must-read-paper` / `route-representative` 都有正文简要论述，并链接对应论文精读 HTML |
| 参考文献列表 | 覆盖所有目标论文、核心 survey、must-read 论文精读页、站内既有相关文章 |

## 4.3 · 配图策略

学术调研的配图逻辑与历史叙事**完全不同**：论文本身就是最权威的图片来源，AI 生成的"架构图"在学术场景中毫无意义——它不能忠实反映方法设计，反而会误导读者。

### 配图优先级

| 优先级 | 来源 | 适用场景 | 工具/方法 |
|--------|------|----------|-----------|
| 优先级 | 来源 | 说明 |
|--------|------|------|
| 🥇 | 用户截图/笔记中的图片 | 最高优先级 |
| 🥈 | arXiv source / arXiv HTML 页面中的原图 | 作者原始 figure 或 HTML 版 figure URL |
| 🥉 | 官方项目页 / GitHub repo 中的配图 | README/docs/assets 中的官方图 |
| 第四 | 高 DPI PDF 裁图 | 300-400 DPI 渲染后裁剪关键 figure |
| 第五 | 代码绘制（mermaid/jsxgraph） | 架构图、流程图补充绘制 |
| 第六 | 网络搜图 | 较少使用，必须本地化并标注 |
| 定位辅助 | Docling referenced 图片 / JSON | 只用于定位 figure、caption、页码，不得作为最终配图 |
| ❌ | AI 生图 | 完全禁止 |

### 论文原图提取流程

1. **arXiv HTML 版本**：优先访问 `https://arxiv.org/html/<arxiv_id>`，直接获取高清矢量图
2. **项目主页**：搜索 `<论文名> project page` 或 `<论文名> github`，获取官方图
3. **PDF 截取**：对 PDF 中关键 figure 用截图工具提取，确保 DPI ≥ 150
4. **图片来源标注**：每个图片的 caption 必须注明来源（如"来源：BLIP-2, Fig. 2"）

### 代码绘制（第三优先级）

当代码绘制的图能比论文原图**更清晰地表达核心思想**时使用：

- **架构/流程图**：用 `{{< mermaid >}}` shortcode
- **数学/函数/信号图**：用 `{{< jsxgraph >}}` shortcode
- 使用场景：多论文架构对比图、简化版方法流程图、时间线图

```html
{{< mermaid >}}
graph LR
    A[冻结 ViT] --> B[Q-Former]
    B --> C[冻结 LLM]
{{< /mermaid >}}
```

### 图片 HTML 格式

```html
<div class="photo">
  <img src="media/images/<slug>/<filename>" alt="描述" loading="lazy">
  <div class="cap">图 N：图片描述（来源：论文名, Fig.N）</div>
</div>
```

### 数量要求

- HTML 正文中至少 3 张关键图片
- 架构对比优先用 mermaid 代码绘制
- 方法示意图优先从论文提取
- 实验结果优先用表格（不用图片）

## Gate 条件

进入 Phase 5 前必须同时满足：

1. **HTML 主文完成**：目标 HTML 已写入 `src/pages/<slug>.html`，frontmatter、分类、`sub_id`、系列导航与 `updated_at` 均正确。
2. **结构完整**：正文包含问题定义、读者导读、任务 taxonomy、技术路线 taxonomy、时间线/演进、方法矩阵、代表论文简要论述、开放问题和小结；系列文章还必须有前后篇导航。
3. **论文覆盖完整**：所有 `must-read-paper` / `route-representative` 都在正文中有简要论述，不能只出现在表格、sources 或图片 caption 中。
4. **图片覆盖完整**：每篇 `must-read-paper` 的核心图片已进入最终 HTML；若缺图，已在 Review 材料中说明原因并用 mermaid/jsxgraph 替代。
