# 方法讲解：先让读者理解它在做什么

适用于论文解读、技术学习笔记，以及用户授权共写的方法类草稿。草稿和正文采用同一可理解性标准；纯素材摘录可以简短，但不要把摘录当作已完成的教学草稿。本规则不改变草稿、OpenSpec、正文之间的审批关系。

## 从任务走到机制

默认先建立整体理解，再深入数学与结构；按方法实际依赖调整顺序，不必套用固定章节数量。

1. **先说清任务和矛盾**：用普通语言说明已有方法哪里不够、输入是什么、希望得到什么。例如“下一段既要接得上，又不能只是重播上一段”，比先罗列三个缩写更能建立问题。
2. **先走一遍完整流程**：从输入到输出说明先后操作、保存或传递的信息，以及这些信息交给谁。区分训练与推理、初始状态与中间状态。模型结构若是理解流程的前提，先给必要的最小介绍，其余细节后置。
3. **逐个引入机制**：先指出当前流程还剩什么问题，再解释新增操作如何缓解它，用小例子展示操作，最后写术语、精确公式或实现细节。不要先堆模块名，再期待读者自己拼出因果关系。
4. **公式承接已经说明的操作**：公式前说它在计算什么、控制什么；定义符号和索引，公式后解释各项对应哪一步。不同时间轴、空间或参数同名时明确区分。先讲直觉不意味着删掉推导。
5. **把机制放回整体**：说明每个机制分别解决哪部分问题，仍然没有解决什么。容易混淆的分工可以用表格总结，但表格不能替代流程解释。

## 用具体例子降低理解负担

- 优先用小规模、能逐步跟随的例子：如A–H表示八份噪声，展示倒序前后；或列出不同位置何时停止复制。
- 明确例子是教学示意还是论文实验配置。类比不能变成论文未证明的机制或效果。
- 缩写首次出现给出全称、中文含义和操作；标题优先回答读者的问题，如“下一段从哪里开始”“怎样产生新内容”。
- 假设读者没读过引用材料，也没看过与作者的聊天。把已获用户认可的清楚解释独立写入草稿，不写“前面回答过”“某回答容易误解”等对话依赖。

## 不以清楚为由牺牲事实

调整组织顺序时保留已确认的重要公式、中间推导、原图、算法、实验表及局限。可以后移细节，不把“先直觉”写成“只讲直觉”。所有机制与效果仍须回原文核验；区分作者的动机、实际操作、教学推导和实验证据。

例如VidRD可以先解释：保存首段轨迹 → 复用初始噪声提供相关起点 → 混入新噪声允许变化 → 借用部分中间状态稳定接缝 → 逐步放开。再展开FNR/PNS/DSG公式和基础网络。不能因此承诺它显式学会了未来事件，或保证连接必然连续。

## 修改与审校

若用户认为答疑比草稿清楚，提取答疑中有效的问题定义、例子、因果链和术语解释，重组对应草稿；不要只在原段落末尾追加一份相同解释。结构变化同步Design，已确认的解释在转正文时继续保留。

审校时，读者应能在不先解析公式的情况下回答：

- 它拿到什么，要生成或求出什么？
- 完整流程先做什么、后做什么，传递了哪些信息？
- 每个新增机制解决哪个具体问题，为什么只用前一步还不够？
- 哪些部分需要训练，哪些是推理时的操作？
- 公式怎样对应前述操作，方法仍有哪些局限？

若只能复述缩写和组件，却说不清上述流程，先改解释顺序和例子，再补网络细节。
