一句话总结：Avatar Forcing、Wan-Streamer、UniLS 把"边听边说"的实时交互做通了，但它们生成的都是有预设长度的回应。OmniMate 处理的是更难的开放式设定：模型不知道该说多久、什么时候该停下回到聆听状态。它的答案是一个显式的生成进度控制器（GPC）加一个多参考条件模块（MRCM），在联合生成视觉+语音+音效的同时保持多轮对话中的身份一致。
问题
开放式交互的两个新难题

把统一音视频生成推到实时交互流式，会撞上两个在离线生成里不存在的难题#Song2026OmniMate#：

难题一：生成地平线未知

常规音频驱动视频生成的每段语音是预先定义好的——"这段音频 8 秒，生成 8 秒视频"。但在开放式交互里，模型根据用户指令持续生成回应，没有人事先告诉它指令的内容是否已经表达完毕。固定时长会截断未说完的回应或产生冗余的语音和动作；显式的"完成检测"模块又会引入额外延迟，破坏实时性#Song2026OmniMate#。

难题二：长时程跨模态身份漂移

流式生成的历史上下文有限：单张参考图或短时相邻 chunk 在大姿态、新视角下不足以锁住外观，视觉身份会随时间漂移；语音这边，有限的上下文让音色在多轮对话间难以保持一致#Song2026OmniMate#。库内精读三十（Avatar Forcing）和三十一（Wan-Streamer）解决的是"怎么实时交互"，OmniMate 补的是"实时交互怎么长期稳得住"。

方法一
GPC：给每个 chunk 一个显式的进度条

GPC（Generation Progress Controller）的思路非常直接：与其让模型自己猜"我说完没有"，不如直接告诉它"你说到整个回应的百分之多少了"#Song2026OmniMate#。

具体机制：给定 LLM 估计的执行时长，确定需要生成的 token 数，给每个位置分配 1–1000 的连续进度值——视频帧按 $p_i^v = 1 + \frac{i-1}{T_v-1} \cdot 999$ 分配（首个 video latent 对应单帧、后续每个 latent 压缩 8 帧，所以帧级进度嵌入按 8 帧一组聚合对齐），音频 token 同理；超出预测执行时长的位置一律赋进度值 0，代表聆听状态#Song2026OmniMate#。进度信号经正弦位置编码 + MLP 后直接加到对应模态的 latent 上（这个注入方式沿用了 OmniAvatar）。

训练上有个精巧的设计：状态转换监督数据来自 DMD 蒸馏后的双向 teacher——用二段式文本交叉注意力 mask（执行段 attend 执行 prompt，聆听段 attend 通用聆听 prompt）构造"仅执行 / 执行→聆听 / 聆听→执行 / 聆听→执行→聆听"四类转换序列。作者特别解释了为什么不用原始多步扩散 teacher：它有时间上的 prompt 泄漏——语义信息会越过预定义的转换边界渗透，导致实际转换点偏离标注#Song2026OmniMate#。这是个很务实的工程洞察：蒸馏 teacher 不只影响效率，还影响监督信号的质量。

GPC 的三重效果

  • 回应按预期进度完成——不截断、不冗余
  • 执行↔聆听状态无缝切换——进度值到 0 即回到聆听
  • 进度感知条件抑制旧 chunk 的影响——新指令到达后立即执行、低延迟切换
方法二
MRCM：多参考图 + 参考语音的持久身份锚

MRCM（Multi-Reference Conditioning Module）分视觉和声音两路#Song2026OmniMate#：

  • 视觉侧：不再依赖单张参考图，而是用 $N$ 张多角度参考图编码成 latent 提供持久的外观线索——多视角身份信息在大姿态、新视角下的鲁棒性远高于单图。消融数据支撑了这一点：去掉多参考视觉条件后 V-ID 从 0.957 降到 0.949。
  • 声音侧：一个 training-free 的说话人条件策略——用模型自己生成的一段固定 warm-up 语音初始化，去噪过程中把生成的音频 latent 替换为参考语音 latent；不提供参考音频时保留原始生成。靠这个持续替换，音色在整个长序列中保持稳定。
OmniMate 方法总览：GPC 进度条件注入 + MRCM 多参考身份保持，统一流式框架内联合生成视觉、语音与音效（图源：arXiv 2607.23023）

消融的分工非常清晰：GPC 系（GPC/teacher/数据构造）全部作用于语音正确率——开放式交互里"说错/说漏/说多"本质上是进度感知问题；MRCM 作用于视觉身份——两个模块正交，各自守一个维度。

解读
把"全双工"往开放式推了一步

在库内的坐标系里，这条交互主线的演进是：Avatar Forcing（精读三十）用扩散强制做实时轮转对话 → Wan-Streamer（精读三十一）单 Transformer 端到端全双工 → UniLS（精读二十八）统一说-听角色 → OmniMate 把回应长度从"预设"变成"自感知"，并第一次把音效（如鼓掌声）纳入联合生成。GPC 处理的"何时收尾"问题，在库内系列十四（后端 Agent 设计）里对应的是轮次检测（VAD/turn-taking）模块——OmniMate 把它从外挂规则变成了生成模型内部的进度条件，这是一个架构层面的信号。

值得注意的局限：评测在交互版 VerseBench 上进行，基线（Ovi、MOVA、LTX）多为离线通用音视频模型而非专门的交互 avatar 系统，跨基准比较需谨慎；TTFF 3.49s 距离"秒接"的商用体验仍有距离；GPC 依赖 LLM 估计执行时长，估计偏差如何传播到进度条件，文中未展开分析#Song2026OmniMate#。
