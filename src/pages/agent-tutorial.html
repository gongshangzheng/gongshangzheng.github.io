Agent 产品

可以先用一个简单的分工来理解：Agent 更像负责安排工作的环境，它连接你的项目、理解任务，再调用工具完成具体操作；模型则提供理解和生成内容的能力。Codex、Claude Code、Pi Agent、Kimi Code、ZCode 和 DeepSeek Harness 属于前一类；Kimi、GLM 等也提供模型或 API 服务。一个厂商同时提供 Agent 和模型，并不代表它们是同一个产品；Agent 能不能使用某个模型，还要看它支持什么接口、怎样配置。

第二章
模型与付费方案

Codex 是你使用 Agent 的入口，理解任务和生成代码的能力来自模型。连接哪家模型服务、如何计费，也要分清账号订阅与 API Key。

模型服务

Agent、模型与 API

可以把它们的分工简单记成三件事：Codex 是你工作的入口；模型服务提供理解和生成能力；API 则是软件向模型服务发送请求时遵守的接口约定。API Key 是平台发给你的访问凭证，类似一把钥匙——它让程序能够代表你发起请求，但它本身不是模型，也不是 Agent。#OpenAI-Codex-Learn##DeepSeek-API-Docs##Zhipu-OpenPlatform-SDK##Kimi-API-Overview#

平时在网页或 App 里聊天，平台已经替你处理了模型调用；使用编程 Agent 时，客户端可能会让你选一个服务，或填写 API Key、接口地址和模型名称。不同产品的设置方式不一样，但都可以先从这个问题入手：这款 Agent 准备连接哪一家模型服务？

费用方案

订阅、API Key 与 Agent

这里最容易产生的误会是：“我已经买了某个聊天产品的会员，是不是就能把它接进编程 Agent？”不一定。会员通常对应某个面向个人的产品或套餐；API Key 则来自开发者平台，供程序调用模型。它们可能有不同的账号入口、额度和计费规则，具体是否包含在某个套餐里，要看服务商当时的说明。以 OpenAI 为例，ChatGPT 和 API Platform 的账单管理是分开的；其他平台也应分别核对自己的规则。#OpenAI-API-Billing##Kimi-API-Overview#

所以，可以先把三个名词分开记：Agent 是工作入口，模型服务提供能力，API Key 是调用服务时使用的凭证。等会儿配置时，Key 就像密码一样保管，不要贴进文章、聊天记录或代码仓库；如果你还没有自己的 API 凭证，现在先理解它的作用就够了。

Harness 工作方式

先把两个词分开：Harness 不是某个具体 Agent 产品的名字，而是围绕模型运行的那套框架；Harness Engineering 则是把这套框架设计好、不断改进的工程实践。它处理的不只是“给模型几个工具”，还包括把哪些项目背景放进上下文、提供哪些操作、怎样限制这些操作，以及怎样把结果反馈给模型。OpenAI 分享 Codex 团队的实践时，也把重点放在设计适合 Agent 的工作环境、明确任务意图和建立反馈循环上。#OpenAI-Harness-Engineering#

模型、Harness、工具和 Agent 的分工如下：#OpenAI-Function-Calling# #Anthropic-Tool-Use# #OpenAI-Harness-Engineering#

部分负责什么编程场景里的例子
大语言模型根据收到的上下文理解任务，生成文字答复，或提出结构化的操作请求。判断可能要先检查登录相关代码。
Harness准备上下文和可用工具，接收模型输出，按规则执行操作，再把结果交回模型。将项目约定、工具说明和读取到的代码组织起来，并控制文件访问范围。
Tool真正执行某一种操作。读取文件、搜索代码、编辑文件或运行测试。
Agent读者实际使用的完整工作系统，通常把模型、Harness、工具和运行环境组合在一起。Codex、Claude Code 等编程 Agent。

工具调用流程

在一次模型请求里，Harness 可以一并提供当前任务、相关项目背景，以及可用工具的名称、用途和参数格式。比如，Read 工具可以说明自己负责读取文件，并要求提供文件路径。模型看到这些说明后，既可以直接用文字回答，也可以在需要操作时按约定格式提出调用请求。这个请求只是“想做什么”的结构化表达，并没有真的读取你的硬盘。#OpenAI-Function-Calling# #Anthropic-Tool-Use#

接下来才轮到 Harness：它检查请求是否有效、当前权限是否允许，必要时停下来请你审批，然后再让对应工具执行。文件内容、测试输出或错误信息会被送回模型的上下文；模型读到结果后，可以继续请求下一步操作，也可以直接给出答复。模型并不是每说一句话都在调用工具；只有需要额外信息或外部操作时，才会走这条路径。#OpenAI-Function-Calling# #OpenAI-Agent-Approvals-Security#

一次常见的工作循环：你提出目标 → Harness 准备上下文和工具说明 → 模型直接回答或提出工具请求 → Harness 检查权限并调用工具 → 工具结果回到上下文 → 模型继续处理，或向你说明结果。

模型提出操作请求，Harness 才负责检查权限、调用工具并传回结果。

工具结果回传

比如你让 Agent 查一下登录失败的原因。模型可能先请求读取登录相关文件；Harness 调用读取工具后，把相关代码交回模型。模型发现一个可疑条件，再提出编辑请求；改完后，它还可以运行测试。若测试失败，报错信息又会回到上下文，让模型据此继续修正。Read、Edit 只是方便理解的叫法，不同 Agent 的工具名称和内部实现可能不同；关键是工具真的去读取、修改或检查外部内容，结果再被提供给模型。工具也不一定都在本机运行：有的由本地 Agent 在受限工作区执行，有的由服务端完成，再把结果返回；具体边界取决于产品设计。#OpenAI-Codex-CLI# #OpenAI-Function-Calling# #Anthropic-Tool-Use#

这也说明了 Harness Engineering 为什么不等于“多写几句提示词”。如果 Agent 总是漏跑测试，单纯要求它“认真一点”未必有用；更有效的办法可能是把测试命令写清楚、让它能调用测试工具，并确保测试结果能反馈回来。Harness Engineering 关注的正是怎样把任务背景、可用操作、执行边界和检查结果组织好，让 Agent 更容易把工作做对。#OpenAI-Harness-Engineering#

上下文与权限

以“修复用户登录失败，并补上回归测试”为例，Harness 不会把整个仓库一股脑塞进上下文，而是按任务挑选需要的信息：

信息来源本次任务中的内容
任务请求修复登录失败，并增加回归测试。
AGENTS.md适用指令文件的完整内容，例如项目技术栈、认证模块的目录或修改约定、测试命令；Codex 按路径作用范围发现文件，不逐条筛选规则。
相关代码与执行结果搜索定位到的认证代码、读取后的相关片段，以及测试输出或报错；随着任务推进按需补入。
工具说明搜索、Read、Edit 和测试工具的用途及参数格式。
Skill如果有适用的认证排查 Skill，再提供其中的任务步骤和相关参考资料，例如追踪认证流程、检查权限判断、补充回归测试；其他 Skill 不必一并加载。

模型拿到的是完成当前任务所需的背景，不是整个项目的副本。Codex 会按路径作用范围发现适用的 AGENTS.md 文件，并把发现文件的完整内容合并进指令上下文；这里选择的是适用的文件，不是逐条挑选文件里的规则。默认合并总量上限为 32 KiB。任务继续推进时，Harness 会把新读到的代码、测试结果等补进上下文；对话变长后，也需要整理历史和任务状态。具体筛选、摘要和加载方式因产品而异，Skill 的脚本也不等于全部都要作为文本塞给模型。#Codex-AGENTS-MD# #OpenAI-Harness-Engineering# #OpenAI-Function-Calling# #OpenAI-Codex-Skills#

权限和上下文也要分开看：上表里的内容告诉模型项目约定和可用操作，沙箱、工具权限与审批规则才决定操作实际能否执行。以 Codex 为例，沙箱设置文件和网络访问范围，审批规则决定某些操作是否要征求同意。读取或修改工作区外文件、访问网络或运行高影响命令，可能需要审批，也可能被禁止；具体取决于产品和当前设置。不能只靠在提示词里写一句“不要越界”来代替权限控制。#OpenAI-Agent-Approvals-Security#

项目长期约定写在 AGENTS.md；某类任务反复使用的处理步骤整理成 Skill。第四章会把上下文、AGENTS.md 和 Skill 放在一起讲清楚，之后再介绍如何规划复杂任务。想深入了解 Harness 的设计方法，可以阅读站内的[[@Harness Engineering：如何让 AI 编程 Agent 可靠地工作]]。

第四章
上下文、AGENTS.md 与 Skill

模型每次回答时都要依据一批信息，这批信息就是它当前的上下文。它可能包括你刚提出的任务、项目规则、Agent 读取到的相关代码、工具返回的测试结果，以及这次任务适用的 Skill 指令。上下文不是整个仓库的副本；Agent 会按产品机制和任务需要筛选、补充信息，Skill 也不一定会在启动时完整加载。

{{< mermaid >}} flowchart TB U["本轮任务请求"] --> C["模型上下文（按需组织）"] A["作用范围内的 AGENTS.md 文件全文"] --> C S["匹配的 Skill 指引（按需加载）"] --> C R["相关代码与工具结果（随任务补充）"] --> C D["可用工具说明与参数"] --> C C --> M["模型生成文字答复或工具请求"] M -->|文字答复| F["返回结果"] M -->|工具请求| P["执行边界：沙箱、工具权限与审批"] P --> T["工具执行"] T --> R {{< /mermaid >}}

任务背景和工具说明可能进入上下文；沙箱、权限与审批则决定工具请求能否执行。#OpenAI-Harness-Engineering##OpenAI-Function-Calling##OpenAI-Agent-Approvals-Security##OpenAI-Codex-Skills#

对 Codex 来说，先按文件的目录作用范围确定哪些 AGENTS.md 适用于当前工作，再把这些文件的完整内容合并进指令上下文，默认总量上限为 32 KiB。匹配的是文件，不是模型逐条筛选文件中的规则；模型拿到全文后再结合当前任务理解要求。其他 Agent 的发现和加载方式可能不同。#Codex-AGENTS-MD#

理解上下文之后，先看两种经常会放进其中的内容：一类是每次做项目都要遵守的约定，另一类是遇到特定任务时才需要的工作流程。

AGENTS.md

刚打开一个项目时，你可能得先告诉 Codex：这里用什么语言、测试要怎么跑、改动时要注意哪些习惯。任务一多，这些背景就容易反复解释。AGENTS.md 可以把常用约定写下来，让 Codex 在开始任务时读取它们；你可以先把它当成一份给 Agent 的“合作说明”。#Codex-AGENTS-MD#

作用范围与加载

有些偏好不管做哪个项目都适用，比如希望 Codex 默认用中文交流；另一些只属于某个仓库，比如这个项目的测试命令或代码风格。把两类规则分开写，既不会让每个项目都重复维护个人偏好，也不容易把某个项目的特殊要求带到别处。

文件适合写什么生效范围
~/.codex/AGENTS.md跨项目都适用的个人习惯，例如偏好中文回复、改动前先说明计划。默认作为个人全局指令；如果设置了 CODEX_HOME，文件位置会随之变化。#Codex-AGENTS-MD#
项目目录链中的 AGENTS.md项目专属信息，例如测试命令、目录结构、格式要求和修改边界。从项目根目录到当前工作目录逐级检查，对相应目录范围生效。#Codex-AGENTS-MD#

Codex 会在开始一轮任务时建立指令链：先读取全局指令，再从 Git 项目根目录一路检查到当前工作目录，每个目录层级最多采用一个指令文件。被发现的非空文件会按目录层级合并，加入指令上下文的是文件完整内容，而不是从中挑出的几条规则；默认合并总量上限为 32 KiB。也就是说，Codex 按路径范围匹配适用的文件，模型再结合任务理解文件中的要求。#Codex-AGENTS-MD#

编写与验证

AGENTS.md 不需要写成长篇手册。全局文件里可以放“默认用中文回复”“新增依赖前先询问”这类个人偏好；项目文件里则写“修改功能后运行项目测试”“先沿用现有组件和命名方式”这样的仓库规则。越具体、越容易判断是否做到，越能帮上忙。

如果项目比较大，也可以把不同目录的要求放在各自的子目录中。比如全仓库都适用的约定放在根目录，某个模块独有的规则再放进模块目录；Codex 会把一路发现的文件合并起来。#Codex-AGENTS-MD#

新开一轮任务时，可以先对 Codex 说：“请先用几句话总结当前项目的约定，再开始处理这个任务。”如果总结漏掉了你写的内容，检查一下文件是不是放在当前项目目录、名称是否正确，以及内容是否为空。Codex 在一轮任务开始时建立指令链；修改 AGENTS.md 后，重新开始一轮更容易确认新规则是否生效。#Codex-AGENTS-MD#

一个简单的分法：对所有项目都适用的习惯放进个人全局文件；只属于当前代码库的要求放进项目根目录。不要把 API Key、密码或其他秘密写进 AGENTS.md，也要先检查从网上下载的项目是否包含自己不认可的指令。

AGENTS.md 适合放每次处理项目都要遵守的约定。更具体、只在某类任务中用到的流程，可以整理成 Skill。#OpenAI-Codex-Skills#

Skill

比如你准备提交代码时，才需要按固定步骤检查改动。每次从头解释既麻烦，也容易漏掉细节；把流程整理成 Skill，就能在需要时交给 Agent 使用。#OpenAI-Codex-Skills#

工作流与调用

一个 Skill 通常是一个文件夹，里面必须有 SKILL.md，写明它的名称、适用场景和操作说明；也可以附上参考资料或脚本。Codex 会先根据 Skill 的名称和简介判断它是否与当前任务有关，再在需要时读取完整说明。你可以明确点名要用哪个 Skill，也可以把任务说清楚，让 Codex 根据简介选择；具体入口会因客户端而异。#OpenAI-Codex-Skills#

内容主要回答的问题例子
AGENTS.md这个项目平时要遵守什么约定？测试命令是什么、修改时要遵循哪种代码风格。
Skill遇到某类任务时，按什么步骤完成？提交代码前，怎样系统地检查改动。
普通提示词这一次具体要我做什么？请帮我检查刚改的登录逻辑。
ToolAgent 可以实际执行哪些动作？读取文件、搜索代码或运行测试。

假设你希望每次审查代码时，Agent 都先找可能的错误和回归，再检查测试是否覆盖到，最后把问题按轻重缓急列出来。只在这一轮任务里做一次，就直接写进提示词；如果以后经常要按同一套步骤检查，可以把它保存成一个名为 review-changes 的 Skill：

review-changes/
└── SKILL.md

---
name: review-changes
description: Review code changes for bugs, regressions, and missing tests.
---

检查本次改动及相关代码，优先寻找可能导致错误或回归的问题。
指出问题时，说明影响、文件位置和建议；没有发现问题时，也说明检查范围。

这个说明不负责读取文件或运行测试——那是 Agent 的工具在做的事。Skill 负责告诉 Agent：什么情况下该走这套流程，以及每一步该关注什么。如果希望同一个仓库的协作者也能使用，可以把 Skill 放进仓库的 .agents/skills/ 目录；只供自己使用的 Skill，则可以放在个人的 ~/.agents/skills/ 目录。Codex CLI 或 IDE 扩展支持用 $review-changes 显式点名 Skill，也可以按任务描述自动匹配。#OpenAI-Codex-Skills#

搜集站与推荐

如果你还不想自己从头写，可以先看看社区里有没有人整理过类似的工作流程。SkillHub、skills.sh 和 SkillsMP 都可以作为发现入口；先把它们当作搜索目录，而不是“找到就放心安装”的清单。#SkillHub-Directory# #Skills-Sh-Directory# #SkillsMP-Directory#

也可以按自己要完成的事情挑选。例如，想做一份适合网页展示、可以横向翻页的演示，可以看看归藏 PPT Skill；它生成的是单文件 HTML。若希望得到能在 PowerPoint 里继续编辑的文件，PPT Master可以作为另一个方向，它的项目说明介绍了原生可编辑 `.pptx` 的生成工作流。做科研时，Scientific Agent Skills则汇集了文献检索、实验设计、数据分析和科研写作等工作流。它们解决的问题和产出的东西并不一样，先看自己需要的是网页演示、PowerPoint 文件，还是科研任务流程。#Guizang-PPT-Skill# #PPT-Master# #Scientific-Agent-Skills#

安装前检查

不必因为某个 Skill 标着“精选”或很热门，就马上安装。先回到原始仓库，读一读 SKILL.md，看清安装命令和附带脚本会做什么：它们可能会读取文件、访问网络或执行命令。不要把 API Key、密码等敏感信息交给不熟悉的 Skill，也尽量只给它完成任务所需的权限。#OpenAI-Codex-Skills# #SkillHub-Directory# #SkillsMP-Directory#

简单记：项目的长期约定写进 AGENTS.md；只在特定任务中反复使用的流程整理成 Skill；临时要求留在提示词里；真正读写文件、搜索或测试，则由工具来完成。

任务跨越多个模块时，先把目标和完成标准拆清楚，通常比直接让 Agent 自行发挥更容易得到预期结果。下一章会用 OpenSpec 说明怎样规划和执行。

第五章
规划与执行

改一个错别字通常不需要正式计划；但如果要新增一项功能，改动会涉及接口、页面和测试，直接让 Agent 开始写代码，容易漏掉边界条件。先把目标、范围和完成标准列出来，你可以先检查方向是否正确，Agent 也能按步骤推进。

计划与执行

规划流程

  1. 说明目标和边界：描述希望得到什么结果、哪些内容不在本次范围内，以及必须遵守的限制。
  2. 让 Agent 调查并列计划：先检查相关代码，再列出涉及的文件、执行步骤、测试方式和仍需确认的问题。
  3. 审阅计划：补充遗漏或改正理解偏差；范围和方案确认后，再让 Agent 开始修改。
  4. 分步执行和核验：Agent 完成每一步后检查结果、运行测试；如果发现新情况，就先更新计划再继续。

模型选择

规划和执行不一定非要用同一个模型。需求复杂、边界容易理解错时，可以先用能力更强的模型梳理方案，再把清楚、可检查的步骤交给成本较低的模型执行；如果任务本身很简单，直接让一个模型完成就够了。是否省 Token，取决于任务难度、套餐额度和实际调用量，不能只凭“规划用强模型、执行用弱模型”保证。

OpenSpec

计划文件分工

OpenSpec 是一种把需求、设计和执行步骤放进同一项变更（change）里管理的方式。以常见的 spec-driven 工作流为例，不同文件承担不同任务：#OpenSpec-Official#

文档记录什么
proposal.md为什么要做、这次要解决什么问题。
design.md准备怎么做，以及需要考虑的结构和取舍。
spec.md必须满足什么要求，怎样判断结果合格。
tasks.md把工作拆成可检查、可逐项完成的任务。
{{< mermaid >}} flowchart LR I["目标与范围"] --> P["Proposal：动机与范围"] P --> D["Design：实现方案"] P --> S["Specs：验收要求"] D --> T["Tasks：执行步骤"] S --> T T --> R{"人工审阅"} R -->|确认| E["分步执行"] R -->|需补充| D E --> V["测试与验证"] {{< /mermaid >}}

在常见的 spec-driven 流程中，Proposal 明确问题和范围，Design 与 Specs 分别描述方案和验收要求，Tasks 再把工作拆成执行步骤。

计划的价值不在文件有多少，而在于执行前能看清范围、步骤和验收方式。小任务用几条清单就够；复杂任务再使用完整的变更计划。计划也不是保证正确的答案，实施中发现事实不符时，应先修订计划，再继续执行。

第六章
安全与复核

Agent 能读写文件、运行命令，也可能把内容发送给模型服务。把敏感信息和权限边界处理好，再检查它实际做了什么，是日常使用中不可省略的两步。

安全使用

密钥与第三方服务

API Key、密码和访问令牌不要写进提示词、代码、AGENTS.md、Skill 或截图。调用 API 时，把密钥放在环境变量或专门的密钥管理工具中；如果意外泄露，尽快撤销并重新生成。将代码交给第三方模型服务或中转服务前，也要先了解数据如何处理，只发送完成任务所需的信息。#OpenAI-API-Docs#

权限限制

开始任务前，确认 Agent 能访问哪些目录、是否可以联网、哪些命令需要审批。只开放完成任务所需的范围；删除文件、修改工作区外内容、联网或执行高影响命令时，先看清操作并按需确认。第三方 Skill 也要检查来源、指令和脚本，不能因为它出现在目录里或标注“精选”就直接信任。#OpenAI-Agent-Approvals-Security# #OpenAI-Codex-Skills#

结果复核

差异检查、测试与回退

任务结束后，先看文件差异和 Agent 的说明，再运行与改动相关的测试。可以用 git status 确认改了哪些文件，用 git diff 检查具体内容；发现无关改动或测试未通过时，先让 Agent 解释并修正，不要只凭一句“已完成”就接受结果。保留版本控制或其他可恢复方式，出错时才能安全回退。

记住三点：敏感信息不外发，只给 Agent 完成任务所需的权限，交付前亲自检查改动和验证结果。
