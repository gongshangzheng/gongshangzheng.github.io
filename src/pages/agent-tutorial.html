先把 Agent 和模型分开看

可以先用一个简单的分工来理解：Agent 更像负责安排工作的环境，它连接你的项目、理解任务，再调用工具完成具体操作；模型则提供理解和生成内容的能力。Codex、Claude Code、Pi Agent、Kimi Code、ZCode 和 DeepSeek Harness 属于前一类；Kimi、GLM 等也提供模型或 API 服务。一个厂商同时提供 Agent 和模型，并不代表它们是同一个产品；Agent 能不能使用某个模型，还要看它支持什么接口、怎样配置。

第一章
模型从哪里来？先弄懂 API 服务

看完 Codex 的演示后，你可能会发现：自己在桌面上操作的是 Codex，但回答问题、理解代码的能力来自模型。那模型是从哪里来的？不同服务又该怎么收费？先把这些事理顺，看到“账号”“订阅”和“API Key”时就不容易混在一起。

先认识模型服务和 API

可以把它们的分工简单记成三件事：Codex 是你工作的入口；模型服务提供理解和生成能力；API 则是软件向模型服务发送请求时遵守的接口约定。API Key 是平台发给你的访问凭证，类似一把钥匙——它让程序能够代表你发起请求，但它本身不是模型，也不是 Agent。#OpenAI-Codex-Learn##DeepSeek-API-Docs##Zhipu-OpenPlatform-SDK##Kimi-API-Overview#

平时在网页或 App 里聊天，平台已经替你处理了模型调用；使用编程 Agent 时，客户端可能会让你选一个服务，或填写 API Key、接口地址和模型名称。不同产品的设置方式不一样，但都可以先从这个问题入手：这款 Agent 准备连接哪一家模型服务？

先认识几家常见的模型服务

如果你在国内使用，可以先从 DeepSeek、智谱 GLM 和 Kimi 的官方模型/API 服务了解起。它们都能通过开发者接口提供模型能力，但产品入口、可用模型和调用方式各自不同。选用前不妨先确认 Agent 支持什么接口、自己的账号能用哪些模型，再对照价格页估算开销。#DeepSeek-API-Docs##Zhipu-OpenPlatform-SDK##Kimi-API-Overview#

服务可以先从哪里了解入门时留意
DeepSeek APIDeepSeek 官方 API 文档与开发者平台。查看当前可用模型、请求格式和账号使用规则；不要只凭模型名称判断能否直接接入某个 Agent。
智谱 GLM API智谱开放平台和 GLM 开发文档。可以从官方文档了解可用模型、接口和账号规则；具体能否接入某个 Agent，要看双方的支持情况。
Kimi APIMoonshot AI 的 Kimi 开放平台及 API 文档。Kimi Code 是 Agent 产品，Kimi API 是模型服务接口；名称相近，不代表账号、套餐或接入方式可以互换。

海外也有 OpenAI 和 Anthropic 等厂商提供模型 API。它们可以和 ChatGPT、Claude 等面向个人使用的产品一起了解，但这几种入口不是同一件事：网页产品给人直接使用，API 则供软件按接口规则调用。#OpenAI-API-Docs##Anthropic-API-Docs#

会员、API Key 和 Agent 不是一回事

这里最容易产生的误会是：“我已经买了某个聊天产品的会员，是不是就能把它接进编程 Agent？”不一定。会员通常对应某个面向个人的产品或套餐；API Key 则来自开发者平台，供程序调用模型。它们可能有不同的账号入口、额度和计费规则，具体是否包含在某个套餐里，要看服务商当时的说明。以 OpenAI 为例，ChatGPT 和 API Platform 的账单管理是分开的；其他平台也应分别核对自己的规则。#OpenAI-API-Billing##Kimi-API-Overview#

所以，可以先把三个名词分开记：Agent 是工作入口，模型服务提供能力，API Key 是调用服务时使用的凭证。等会儿配置时，Key 就像密码一样保管，不要贴进文章、聊天记录或代码仓库；如果你还没有自己的 API 凭证，现在先理解它的作用就够了。

订阅套餐和 Coding Plan，分别买到什么

看到价格时先别急着挑最便宜的，因为这些方案卖的不是同一种东西。有的是 Agent 或聊天产品的会员，费用按月或按年收；有的是面向多款编程工具的 Coding Plan；还有 API 按实际调用的 Token 数量计费。它们的使用额度也不一样，不能只把月费放在一起比较。

选择服务前，先看三个实际问题

  1. Agent 能不能接？先看 Agent 支持哪些供应商和请求格式。服务商提供 API，不等于每个 Agent 都能不经设置直接使用。
  2. 怎么使用和计费？确认 API 是否需要单独开通、额度如何计算，以及当前账号是否有可用权限；不要把不同产品的会员和 API 权益想当然地画上等号。
  3. 凭证怎么保管？只从官方平台获取 Key，先了解数据处理和使用条款，并避免把凭证放进项目文件或公开截图。

第二章
项目约定不用每次重说：认识 AGENTS.md

刚打开一个项目时，你可能得先告诉 Codex：这里用什么语言、测试要怎么跑、改动时要注意哪些习惯。任务一多，这些背景就容易反复解释。AGENTS.md 可以把常用约定写下来，让 Codex 在开始任务时读取它们；你可以先把它当成一份给 Agent 的“合作说明”。#Codex-AGENTS-MD#

个人习惯和项目规矩，放在不同地方

有些偏好不管做哪个项目都适用，比如希望 Codex 默认用中文交流；另一些只属于某个仓库，比如这个项目的测试命令或代码风格。把两类规则分开写，既不会让每个项目都重复维护个人偏好，也不容易把某个项目的特殊要求带到别处。

文件适合写什么生效范围
~/.codex/AGENTS.md跨项目都适用的个人习惯，例如偏好中文回复、改动前先说明计划。默认作为个人全局指令；如果设置了 CODEX_HOME，文件位置会随之变化。#Codex-AGENTS-MD#
项目根目录/AGENTS.md项目专属信息，例如测试命令、目录结构、格式要求和修改边界。只对当前项目及其工作目录生效。#Codex-AGENTS-MD#

Codex 会在开始一轮任务时建立指令链：先读取全局规则，再从项目根目录一路检查到当前工作目录。项目里的规则会按目录从外到内合并，因此更靠近当前文件的约定可以补充更具体的要求。#Codex-AGENTS-MD#

先写清楚最常用的几条

AGENTS.md 不需要写成长篇手册。全局文件里可以放“默认用中文回复”“新增依赖前先询问”这类个人偏好；项目文件里则写“修改功能后运行项目测试”“先沿用现有组件和命名方式”这样的仓库规则。越具体、越容易判断是否做到，越能帮上忙。

如果项目比较大，也可以把不同目录的要求放在各自的子目录中。比如全仓库都适用的约定放在根目录，某个模块独有的规则再放进模块目录；Codex 会把一路发现的文件合并起来。#Codex-AGENTS-MD#

怎么确认规则真的被读到了？

新开一轮任务时，可以先对 Codex 说：“请先用几句话总结当前项目的约定，再开始处理这个任务。”如果总结漏掉了你写的内容，检查一下文件是不是放在当前项目目录、名称是否正确，以及内容是否为空。Codex 在一轮任务开始时建立指令链；修改 AGENTS.md 后，重新开始一轮更容易确认新规则是否生效。#Codex-AGENTS-MD#

一个简单的分法：对所有项目都适用的习惯放进个人全局文件；只属于当前代码库的要求放进项目根目录。不要把 API Key、密码或其他秘密写进 AGENTS.md，也要先检查从网上下载的项目是否包含自己不认可的指令。

AGENTS.md 适合放那些每次工作都要遵守的基本约定。遇到更具体、可重复的一类任务时，还可以用 Skill 把步骤整理成按需调用的工作流程；下一章我们就来看看它适合解决什么问题。

第三章
把重复流程交给 Agent：认识 Skill

刚才我们说到，AGENTS.md 适合放项目里经常要遵守的约定。不过，有些工作并不是每次都要做：比如你准备提交代码时，才需要按固定步骤检查改动。每次从头解释一遍既麻烦，也容易漏掉细节。把这类可重复的流程整理成 Skill，就能在需要时交给 Agent 使用。#OpenAI-Codex-Skills#

Skill 像一份可复用的任务流程

一个 Skill 通常是一个文件夹，里面必须有 SKILL.md，写明它的名称、适用场景和操作说明；也可以附上参考资料或脚本。Codex 会先根据 Skill 的名称和简介判断它是否与当前任务有关，再在需要时读取完整说明。你可以明确点名要用哪个 Skill，也可以把任务说清楚，让 Codex 根据简介选择；具体入口会因客户端而异。#OpenAI-Codex-Skills#

内容主要回答的问题例子
AGENTS.md这个项目平时要遵守什么约定？测试命令是什么、修改时要遵循哪种代码风格。
Skill遇到某类任务时，按什么步骤完成？提交代码前，怎样系统地检查改动。
普通提示词这一次具体要我做什么？请帮我检查刚改的登录逻辑。
ToolAgent 可以实际执行哪些动作？读取文件、搜索代码或运行测试。

用代码审查举个例子

假设你希望每次审查代码时，Agent 都先找可能的错误和回归，再检查测试是否覆盖到，最后把问题按轻重缓急列出来。只在这一轮任务里做一次，就直接写进提示词；如果以后经常要按同一套步骤检查，可以把它保存成一个名为 review-changes 的 Skill：

review-changes/
└── SKILL.md

---
name: review-changes
description: Review code changes for bugs, regressions, and missing tests.
---

检查本次改动及相关代码，优先寻找可能导致错误或回归的问题。
指出问题时，说明影响、文件位置和建议；没有发现问题时，也说明检查范围。

这个说明不负责读取文件或运行测试——那是 Agent 的工具在做的事。Skill 负责告诉 Agent：什么情况下该走这套流程，以及每一步该关注什么。如果希望同一个仓库的协作者也能使用，可以把 Skill 放进仓库的 .agents/skills/ 目录；只供自己使用的 Skill，则可以放在个人的 ~/.agents/skills/ 目录。Codex CLI 或 IDE 扩展支持用 $review-changes 显式点名 Skill，也可以按任务描述自动匹配。#OpenAI-Codex-Skills#

先看清内容，再决定要不要用

Skill 能帮你省下重复交代流程的时间，但不用一开始就装很多。先挑一件自己确实反复做、步骤也比较稳定的事，试着写成短小清楚的说明就够了。若使用别人分享的 Skill，先读一遍 SKILL.md，也检查它附带的脚本：脚本可能会读取文件、访问网络或执行命令，不要在没看明白时就运行，更不要让它接触密钥等敏感信息。#OpenAI-Codex-Skills#

简单记：项目的长期约定写进 AGENTS.md；只在特定任务中反复使用的流程整理成 Skill；临时要求留在提示词里；真正读写文件、搜索或测试，则由工具来完成。

Skill 可以告诉 Agent 按什么步骤工作，但要真正检查代码、搜索文件或运行测试，还得依靠工具。下一章我们就来看看这些工具怎样让 Agent 从“会说”变成“能动手”。
