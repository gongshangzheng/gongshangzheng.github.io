# 设计：课题组 AI API 采购选型调研仓库

## Context

课题组需要新购模型 API / 套餐。使用者规模已确认：**1 名老师 + 2 名博士 + 3 名硕士，共 6 人**；主要任务场景已确认为**做研究 + 写文档**两类；各场景频率、预算、支付与合规待盘点（任务 1.3）。候选范围三类：

1. **模型供应商**（用户点名：Kimi、DeepSeek；追加：GLM/智谱、MiniMax、xAI Grok；国外 ChatGPT 已有但不够用）
2. **Agent 平台订阅**（把模型打包进 IDE/CLI 订阅，常比裸 API 便宜）：Qoder（阿里）、WorkBuddy（腾讯云 CodeBuddy 团队）；对照 Cursor、Copilot、Trae；另有 OpenCode Go（$10/月订阅，含 30+ 开源模型，发 API key）
3. （仅作参考基线）本机已有 5 源个人配置（zai/kimi/minimax/deepseek/codestral），不代表课题组用量

约束：国内网络，国外源需走 VPN（遵循 web-search skill 探测规范）；课题组支付方式、发票与数据合规要求待盘点；组内使用模式未知，需先画像。

## Goals / Non-Goals

**Goals:**
- 三类数据（价格 / 权威测评 / 需求画像）全部脚本化或结构化，可重复运行、可追溯
- 每个"谁擅长什么"的结论落到证据 ID；流行说法给出证实/证伪/证据不足三态结论
- 产出可执行的采购决策：决策矩阵 + 分级建议 + 最小额度试点方案 + 接入指南

**Non-Goals:**
- 不自动购买、不代管账号；不做统一 LLM 网关/代理
- 不追求覆盖全网模型与平台，只覆盖点名候选 + 强相关对照
- Agent 平台不单独做能力测评——能力随其包含的底层模型走，引用模型证据即可
- 不在本 change 中发布博客文章（另起 change）

## Decisions

1. **独立仓库 `~/code/ai-api-research`**：数据快照与博客无关，独立 git 便于开源/迁移。备选（放博客仓库）被否：职责混杂。
2. **技术栈 Python 3 + httpx + rich**：与 arxiv-paper-digest 管线同栈。备选 TypeScript（全局规范）被否：调研脚本生命周期独立。
3. **价格数据源分品类分两层**：
   - 模型 API：官方定价页为主（per-source 独立解析器），LiteLLM / models.dev / OpenRouter 三社区源交叉验证，偏差 >20% 标 `CONFLICT`；补充源（tokencost、genai-prices、Portkey-AI/models、awesome-free-llm-apis 等 GitHub 已有仓库）作备选交叉
   - **渠道优先级（重要）**：同一模型在 litellm 里常同时有官方直连价与一堆转售商（fireworks / deepinfra / novita / aihubmix ...）低价，取“同源最低”会把转售价当成官方价（曾导致 GLM-5.3 显示 $0.06）。因此按 tier 分层取价：tier0 厂商直连 > tier1 聚合平台 > tier2 第三方转售，报告中标注渠道。
   - **只展示当前主力模型**：白名单 `data/current_models.json`（每家族 2 个，含跨源别名归一），历史变体与转售渠道只存快照不展示。
   - Agent 平台：多为 JS 动态营销页且无社区结构化源可比 → 静态抓取优先，失败降级"文本抓取 + 人工核实卡"，记录强制含 URL + 抓取时间
4. **订阅套餐（两品类）半自动采集**：营销页/需登录，脚本抓页面文本 + 人工核实，报告标注"人工核实日期"。
5. **证据收集"脚本抓取 + 人工证据卡"混合**：可结构化源（Artificial Analysis、LMArena）脚本抓；PDF 报告（SuperCLUE 月报）人工读数录入 YAML 卡；四要素（来源/榜单/日期/URL/数值）强制必填。
6. **需求画像代替日志审计**：结构化问卷/访谈清单盘点场景、频率、预算、支付与合规；人数已确认（6 人：1 老师 + 2 博士 + 3 硕士），用量估算按角色分层假设——老师为审批与中低频场景，博士/硕士为研究主力高频场景；用"场景频率 × 单次 token 规模"模型输出轻/中/重三档与敏感度区间。本机 pi 日志仅作个人参考附录，不得作为采购档位依据。
7. **Agent 平台的专项评估维度**：模型配额与限速条款、平台锁定（仅官方 IDE/CLI 可用 vs 开放 API/兼容协议）、团队 seat 计价（按课题组 6 席折算总成本）与协作功能、与课题组工作流的兼容性。"平台更便宜"必须折算到画像同等用量下比较，禁止拿标价直接比。
8. **决策交付四件套**：决策矩阵（供应商/平台 × 档位 × 场景 × 预估月成本 × 风险）、分级建议（主力/备选/专项）、任务→模型→Harness 分工表、最小额度试点方案（验证限速/并发/稳定性/封号风控/实际质量，通过标准事先写明）。配置与购买由课题组管理员执行。
9. **用量统计管道分层采集**：优先供应商用量 API 自动拉取（可得性逐家核实），控制台导出手动导入为中层，客户端 harness 日志兑底；场景标签由"工作目录/项目 → 场景"映射表自动生成（初始场景：研究、写文档），不做逐条人工打标；隐私边界：仅统计字段（人/场景/模型/token/费用/时间），永不采集提示词与回复正文。
10. **反代可行性三态评估、合规优先**：按认证机制（API Key / OAuth 设备绑定 / 指纹）+ ToS 条款引用 + 社区实践仓库佐证（free-one-api、kiro-gateway、cc-gateway 等逆向项目证明技术可行性同时证明封号风险真实存在），对每家给出 GATEWAY_OK / GRAY_RISK / NOT_FEASIBLE 三态结论；合规立场：GATEWAY_OK 为唯一推荐路径（LiteLLM / one-api / new-api 网关 + per 成员配额），GRAY_RISK 仅作风险披露不推荐，由课题组在知情前提下自行决断。
11. **展示页为自包含静态 HTML**：`fetch/render_site.py` 从数据文件生成 `site/index.html`，无框架无构建，浏览器直接打开；套餐档案落盘为结构化 `data/plans.json`（同时是套餐半自动采集的数据载体）；暂不部署，后续可选 GitHub Pages。

## Risks / Trade-offs

- [Agent 平台定价页动态渲染难抓] → 降级半自动核实，不硬写爬虫；四要素保可复核
- [平台套餐低价伴随配额/限速/模型降级] → 决策矩阵强制列配额条款；试点实测速度与降级行为
- [账号共享违反 ToS / 封号] → 接入指南列子账号/团队版/共享三方案的条款与风险，优先团队版
- [订阅反代/逆向接口随平台升级失效] → GRAY_RISK 结论仅作风险披露不作推荐；合规替代（团队版 seat）价格进决策矩阵
- [定价页结构改版] → 解析器按源隔离、失败显式报错，社区源交叉兜底
- [榜单公信力争议] → 白名单多源互证；单一来源不足以支撑"证实/证伪"
- [VPN 不稳定] → 部分成功语义，国外源标 `UNAVAILABLE` 不阻断国内源
- [预算审批周期长] → 试点小额先行，试点报告支撑批量采购审批

## Migration Plan

初始化仓库并确认候选产品 → 数据层（pricing/evidence/profile）→ 报告层 → 决策文档（课题组审核）→ 试点 → 采购落地与接入指南。回滚不涉及系统变更，最坏情况是"调研结论不采纳"，仓库留档即可。
