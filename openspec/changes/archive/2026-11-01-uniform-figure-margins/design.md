# Design: 统一图片留白

## Context

- 正文图渲染规则：`.photo` 卡片包裹时 `img { width: 100% }`；裸图同样受 `.wrap` 的 800px 约束，实际显示宽度约 752px。因此**源图宽度 → 显示宽度是一个近乎固定的缩放比**，留白按源图宽度取固定比例即可得到统一的屏幕留白。
- 已有可复用的背景检测与裁切：`scripts/convert-figures.py:crop_whitespace()` 从四角 10% 区域取中位灰度自适应背景色，支持非纯白底（阈值 247）。
- 已有留白门禁：`scripts/check-figure-whitespace.py`，阈值 20%，只在图片有改动时运行。
- 上一轮优化已把 >4000px 的图降采样，原图备份在 `raw/media-originals/`，派生档由 `lib/media-images.js:ensureVariants` 按源图尺寸生成。
- 存量留白分布：739 张超 4000px 的图已处理，当前被引用图片约 1740 张，其中 7 张留白超 20% 刚被裁过，另有多张零留白。

## Goals / Non-Goals

**Goals:**

- 同一页面内所有静态配图的屏幕留白一致（约 22px 四边）。
- 归一幂等，可重复执行，可回滚（依赖 `raw/media-originals/`）。
- 归一不破坏背景色匹配、透明通道、动效。
- 归一后仍满足上一轮的性能预算（单图 ≤2MB、长边 ≤4000px、派生档齐全）。

**Non-Goals:**

- 不改 CSS 间距（`.photo` 的 28px margin 保持；图内留白与卡片外边距是两层，本次只统一图内那层）。
- 不改图注、不放大小图（不做 upscale）。
- 不处理未被引用的图片（它们不部署）。
- 不处理 `media/pdf`、`media/videos`。

## Decisions

### D1. 留白按源图宽度的 3% 取值，四边等宽

`.wrap` 内容宽度约 752px，3% × 752 ≈ 22.6px，与 `.photo` 的 12~18px 内边距处在同一视觉档位，不会显得空。按源图宽度换算而不是按短边，是因为显示尺寸由宽度决定：竖长图和横长图在屏幕上宽度相同，只有按宽度取比例才能让留白屏幕尺寸一致。

四边取同一个像素值（`pad = round(0.03 * width)`），不做长短边差异化——差异化会让竖长图上下留白过厚。

**Alternatives**：按短边百分比（常见做法）→ 竖长图上下留白明显大于横长图，视觉不统一；按固定像素（如 24px）→ 对小图占比过大、对大图几乎没有效果。

### D2. 补白颜色取该图自身背景色，透明图保留 alpha

复用 `crop_whitespace` 的背景检测结果（四角中位灰度）。实现上用 PIL：`ImageOps.expand(img, border=pad, fill=(bg,bg,bg))`；若原图 mode 含 `A`（`RGBA`/`LA`/`P` 带透明），以 `(bg,bg,bg,0)` 扩展，保持透明。

**为什么不统一填白**：非白底图（检测到 bg≈148、bg≈248 等）会出现白色描边；暗色模式下白边尤其明显。

### D3. 归一顺序：裁 → 补 → 降采样 → 编码

顺序固定为 ① `crop_whitespace` 裁到内容边界 ② 按**裁剪后**宽度补 3% ③ 若长边 >4000px 等比缩到 4000 ④ 存 WebP（q82，method 4）。先补后缩保证留白比例在最终文件里仍是 3%。

派生档由构建期 `ensureVariants` 从归一后的源图生成，比例自然一致，无需单独处理。

### D4. 幂等与豁免

- 幂等：先算内容边界，若「当前留白已等于 3% ±0.5%」则跳过该文件，不重编码。
- 豁免：多帧 WebP（`n_frames > 1`）、SVG、未被引用的图片。
- 备份：`raw/media-originals/` 已有文件不覆盖（保留最早的原图），保证 `--restore` 仍能回到最初状态。

### D5. 实现语言与并行

Python + PIL，复用 `convert-figures.py` 的裁切函数，`multiprocessing.Pool` 按 CPU 数并行。理由：裁切/背景检测逻辑已经存在且经过使用，用 Node 重写一遍等于维护两份实现；上一轮 Node 侧的 sharp 只负责派生档。

CLI：`--dry-run`（默认，输出分布统计）、`--apply`、`--restore`、`--limit N`（抽样试跑）。

### D6. 归一后重跑门禁与预算

归一完成后依次执行：`check-figure-whitespace.py --changed`（必须 0 FAIL）、`node build.js`（派生档重建）、`check-perf-budget.js --check`（体积预算不变）、`npm test`。

## Risks / Trade-offs

- **暗色模式下白底图的留白与图本身同色** → 视觉上只是「图更大一圈」，与现状同类；不会出现与页面背景冲突的描边。若日后觉得白块过重，可在 CSS 侧给 `.photo` 加内边距替代图内留白（一次改动即可回退 D1）。
- **体积增加** → 补白区域是纯色，WebP 压缩后开销很小（估算 +3~8%）。若个别图超 2MB，`--downsample` 的字节预算阶段会继续收口。
- **重编码是有损二次编码** → 原图已在前一轮降采样时编码过一次。为控制累积损失，归一从 `raw/media-originals/` 的备份读取源，而不是从已降采样的 `media/` 读，避免二次有损叠加。
  - 备份缺失的文件（前一轮未曾降采样的小图）直接从 `media/` 读，属于首次归一，无累积问题。
- **1700 张图重编码耗时长** → 并行 + 幂等跳过；预估 5~15 分钟，一次性成本，不进入 CI。
- **门禁误伤** → 归一后留白恰为 3%，与 20% 阈值有足够余量；若某图内容边界检测失败（整图同色），跳过并列入报告，不强行裁切。

## Migration Plan

1. `--dry-run` 出分布报告（当前留白分布、将裁/将补/将跳过数量），用户确认后执行。
2. `--apply` 归一 → 重建 → 门禁 → 测试。
3. 提交并推送，CI 走既有 Pages 流程。
4. 回滚：`--restore` 恢复原图后重建；或 `git revert` 图片提交（git 历史保留旧 blob）。
